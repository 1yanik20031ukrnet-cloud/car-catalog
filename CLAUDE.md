# Инструкции для Claude Code

## О проекте

Демонстрационный mobile-first сайт-каталог автомобилей для небольшого
автосалона. Продавец ставит одну ссылку в bio
Instagram/Telegram/TikTok, клиент видит актуальные машины, фильтрует,
открывает страницу автомобиля и записывается на просмотр.

«Premium Cars Warsaw» — временное демо-название. Первичный рынок —
Украина, но продукт должен адаптироваться под любой автосалон и
похожие Instagram-бизнесы с продажами. Поэтому название салона,
описание, контакты и валюту НЕ зашивать в шаблоны и код — они живут
в базе данных (модель `Dealer` и поля `Car`) и меняются через админку.

Это MVP одного автосалона, НЕ маркетплейс. Но архитектура не должна
мешать будущему развитию: Telegram-уведомления, аналитика просмотров,
избранное, несколько салонов, SaaS.

Список задач и текущее состояние — в `TASKS.md`.

## Стек

- Python + Django 6.1, SQLite.
- HTML-шаблоны Django + чистый CSS (mobile-first), минимум JavaScript.
- Фильтры каталога — через GET-параметры URL, рендеринг на сервере.
- Админ-панель — стандартная админка Django + тема `django-unfold`
  (согласовано с владельцем 2026-08-30, только внешний вид, модели
  и URL не меняет).
- Не добавлять новые фреймворки и библиотеки без обсуждения.

## Модели (план)

- `Dealer` — автосалон: название, описание, телефон, соцсети,
  валюта цен (для Украины обычно $, но должна переключаться:
  ₴ / $ / € / zł). Пока одна запись, задел на несколько.
- `Car` — автомобиль: марка, модель, год, цена, пробег, топливо,
  коробка, объём, мощность, привод, кузов, VIN (опционально),
  описание, внутренняя заметка (`internal_note`, только для админки,
  никогда не выводится в шаблонах сайта), статус (в продаже /
  зарезервирован / продан), slug.
- `CarImage` — фотографии автомобиля (несколько, с порядком).
- `Booking` — заявка на просмотр (машина, имя, телефон, дата, время,
  комментарий).

## О владельцах проекта

Проект делают два начинающих разработчика, каждый со своим Claude Code
и локальной копией. Оба учатся, поэтому:

- объясняй изменения простыми словами, на русском;
- расшифровывай новые термины;
- давай пошаговую инструкцию проверки после изменений;
- объясняй Git-команды человеческим языком.

Код, имена переменных и сообщения коммитов — на английском.

## Совместная работа

- Основная ветка — `main`. Напрямую в `main` не работаем.
- Каждая задача — отдельная ветка: `feature/...` или `fix/...`
  (например `feature/car-models`, `fix/mobile-layout`).
- Workflow: ветка → разработка → проверка → commit → push →
  Pull Request → merge в `main` → второй разработчик делает
  `git pull` в `main`.
- Перед началом новой задачи: `git checkout main` и `git pull`,
  чтобы начать от свежей версии.
- Коммиты в стиле: `feat: add vehicle filters`, `fix: mobile cards`.
- Не переписывать чужие изменения. При конфликте — сначала объяснить,
  где и почему он возник, и предложить безопасное объединение.
- Разделять задачи так, чтобы два человека редко трогали одни файлы
  одновременно (пример: один в `models.py`/`admin.py`, другой в
  `templates/` и `static/`).

## Правила изменения проекта

- Работать маленькими законченными этапами, один этап — один PR.
- Не делать косметический рефакторинг вместе с новой функцией.
- Не менять несвязанные части кода.
- Перед крупным изменением — короткий план и подтверждение владельца.
- Не объявлять задачу готовой без проверки в браузере.
- MVP: не усложнять архитектуру преждевременно.
- **Коммитить только после того, как владелец сам проверил изменение**
  (2026-08-30). Пока владелец не подтвердил — можно вносить правки и
  проверять их самостоятельно (`manage.py check`, браузер), но не
  делать `git commit`. Если за одну задачу было несколько
  доработок/исправлений — это один коммит после подтверждения, а не
  коммит на каждую правку. Так проще разобраться в истории и не
  накапливается много мелких коммитов.

## Workflow для frontend и визуальной разработки

У владельцев может быть установлен разный набор инструментов
(2026-08-31): `frontend-design`, `Playwright CLI` + Playwright skills,
`frontend-visual-qa`, `front-review`, `grill-me`. Ни один из них не
обязателен для работы над проектом (см. пункт 7) — это усилители
процесса, а не часть архитектуры.

### 1. Frontend Design

Для задач, где создаётся или заметно меняется интерфейс — главная
страница, каталог, карточка автомобиля, страница автомобиля, фильтры,
админка, формы, навигация, responsive/mobile UI, новые компоненты —
используй skill `frontend-design`, если он доступен.

Не делать типичный шаблонный AI-интерфейс. Ориентиры проекта:
mobile-first; современный автомобильный каталог; премиальный, но не
перегруженный стиль; акцент на фотографиях машин; хорошая типографика
и понятная визуальная иерархия; каталог важнее декоративного
лендинга, минимум бессмысленных секций; интерфейс должен хорошо
работать для пользователей из Instagram/Telegram и других соцсетей.

Не делать полный редизайн уже согласованного интерфейса без причины.

### 2. Playwright — обязательная проверка визуальных изменений

Если задача меняет то, что пользователь реально видит на сайте, и
Playwright доступен — после реализации самостоятельно проверяй
результат через него. Не спрашивать каждый раз «проверить сайт?» /
«скинешь скриншот?» / «открыть браузер?» — если инструмент доступен,
им нужно просто пользоваться.

Обычный цикл: изменение кода → открыть реальную страницу → проверить
через Playwright → исправить проблемы **текущей** задачи → проверить
снова → только после этого считать задачу выполненной (см. также
пункт 9 и «не объявлять задачу готовой без проверки в браузере» выше).

Проверять как минимум desktop (~1440px) и mobile (~390px), при
необходимости — tablet/промежуточный viewport. Следить за: responsive,
горизонтальным scroll, overflow/clipping, текстом, который не
помещается, наложением элементов, grid/flex layout, размерами и
aspect ratio фото машин, spacing, typography, CTA/кнопками, формами,
фильтрами, dropdown, modal, sticky/fixed элементами, состояниями
интерфейса.

Если проблема возникла из-за текущего изменения — исправить и
проверить повторно. Несвязанные старые проблемы не чинить
автоматически — один раз коротко сообщить о них отдельно.

### 3. Использование браузера

Если доступен инструмент/коннектор для безопасного просмотра открытой
вкладки с локальным проектом — использовать его для визуальной
проверки вместо постоянных просьб прислать скриншот вручную.
Приоритет: 1) доступный browser tool для нужной вкладки → 2) Playwright
→ 3) скриншот от владельца — только если первые два способа реально не
позволяют увидеть нужное состояние, и с объяснением, что конкретно
нужно показать.

Не взаимодействовать с несвязанными личными вкладками, аккаунтами или
данными браузера — только с локальным сайтом или страницами, нужными
для текущей задачи.

### 4. Frontend Visual QA

После заметных визуальных изменений использовать `frontend-visual-qa`,
если доступен — он дополняет Playwright, а не заменяет: Playwright
открывает и исследует интерфейс, `frontend-visual-qa` оценивает уже
отрисованный результат (composition, typography, wrapping, overlap,
overflow, responsive, изображения, spacing, состояния страниц,
визуальные дефекты).

По умолчанию сначала audit; если исправление входит в текущую задачу —
сделать минимальные правки и проверить результат снова.

### 5. Front Review

Не запускать `front-review` после каждой мелкой CSS-правки. Запускать:
после завершения крупной frontend-функции, после каталога, после
фильтров, после страницы автомобиля, после серьёзной части админки,
перед Pull Request (когда уместно), перед крупным frontend merge, или
когда изменения затронули много frontend-кода.

Искать: bugs, потенциальные ошибки, проблемы производительности и
поддерживаемости, плохую структуру, ненужные усложнения. Не делать
крупный рефакторинг только ради красоты кода, если текущая реализация
работает и изменение не требуется (см. «не делать косметический
рефакторинг вместе с новой функцией» выше).

### 6. Grill Me

`grill-me` вызывается вручную владельцем, не автоматически — не
пытаться обходить его настройки или запускать самостоятельно, если
skill запрещает вызов моделью. Используется как `/grill-me plan` перед
крупными/неоднозначными задачами и `/grill-me check` для проверки
результата. Если через него согласован план — учитывать его при
реализации.

### 7. Если skill недоступен

У второго разработчика часть skills или browser tools может быть не
установлена — их наличие не обязательное условие работы над проектом.
Перед использованием проверять доступность в текущей среде. Доступен —
использовать. Недоступен — не ломать задачу, ничего не устанавливать
глобально самостоятельно, не менять `package.json` ради personal
tool, продолжать доступными средствами и в конце один раз коротко
сообщить, какую проверку выполнить не удалось (не повторять
предупреждение многократно).

### 8. Совместная разработка

Здесь действуют общие правила из разделов «Совместная работа» и
«Правила изменения проекта» выше (не перезаписывать чужие изменения,
объяснять Git-конфликты вместо слепого выбора версии, коммитить
только после проверки владельцем). Дополнительно: минимизировать
изменение файлов, не связанных с задачей, и не делать push/merge/
удаление веток без отдельного разрешения, если владелец явно не задал
другое правило.

### 9. Что считается завершённой frontend-задачей

Не просто «код компилируется». При доступных инструментах: код →
реальный запуск → Playwright → visual check → исправления → повторная
проверка; для крупных частей дополнительно — `frontend-visual-qa` и
`front-review`. Цель — чтобы владельцу реже приходилось вручную делать
скриншот сайта и объяснять очевидные визуальные проблемы.

## Безопасность

- Не коммитить `.env`, токены и ключи.
- Не коммитить `db.sqlite3` и содержимое `media/`.
- Не выполнять `git reset --hard` и `git push --force`.
- Перед потенциально опасной командой объяснять её действие.
